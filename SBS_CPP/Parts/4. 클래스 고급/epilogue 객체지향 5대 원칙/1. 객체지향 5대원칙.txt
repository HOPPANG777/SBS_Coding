1>	단일 책임 원칙
	( Single Responsiblity Principle, SRP )
=========================================================================================

	-	소프트웨어의 설계부품은
					( 클래스, 함수 등 )
		단 하나의 책임만을 가져야 함..
					( 기능 )
		 
		ㄴ	책임 영역이 명확해짐..

			ㄴ	수정, 편집에 대한 부작용이
				발생할 확률 감소..


	-	소프트웨어 개발 3대 원칙 중 하나인
		KISS와 유사한 개념..

		ㄴ	KISS..

2>	개방-폐쇄 원칙
	( Open-Closed Principle, OCP )
=========================================================================================

	-	소프트웨어의 구성 요소는
					( 컴포넌트, 클래스, 모듈, 함수 )
		확장에는 열려있고,
				( open )
		변경에는 닫혀있어야 함..
				( close )

	-	변경될 수 있는 부분
		파악에 초점..

		==================================================
			변경 여부..			|	설계 방식..
		==================================================
			자주 변경될 수		|	수정하기 쉽게 설계..
			있는 부분..			|-------------------------
								|	의존 관계, 또는
								|	상속을 통하여 구현..
								|-------------------------
								|	게임에 사용되는 컨텐츠
								|	-	총알, 적, npc 등..
		==================================================
								|	수정되는 내용에 영향을
								|	받지 않도록 설계..
			변경되지				|-------------------------
			않아야할 부분..		|	추상 클래스 또는
								|	인터페이스로 분리..
								|-------------------------
								|	게임 시스템..
								|	-	게임 매니져,
								|		UI 매니져,
								|		스폰 기능 등..
		==================================================
		

	------
	상황..
	------

			class CSoundPlayer
			{
				public :
					void PlayWav()
					{
						cout<< "Wav Play" << endl;
					}
			}

			void main()
			{
				CSoundPlayer sPlayer;
				sPlayer.PlayWav();
			}



	---------------
	수정 사항 제기..
	---------------

		-	CSoundPlayer는 현재 wav 파일만
			재생가능..

		-	요청 발생!!!
			
			-	다른 포맷의 음원 파일
				재생 기능 추가..
			
				ㄴ	mp3나 그 외 음원파일..



	------
	고찰..
	------

		-	[ CSoundPlayer ]는 음원에 따라
			PlayWav() 함수가 다르게
			구현되어야 함..

			ㄴ	[ CSoundPlayer ]를 추상화..

				ㄴ	수정사항에 따라 추가로 적용될
					컨텐츠들과의 공통적인 부분을
					정리하여 부모 클래스를 만들 것..

				ㄴ	음원의 포맷은 다르지만
					재생한다는 기능은 동일하므로
					PlayWav() 함수를 추상 클래스 또는
					인터페이스로 분리..
		

	------
	해결.. 
	------


			class CSound
			{
				public :
					virtual void Play() = 0;
			}


			class CWav : public CSound
			{
				public:
					virtual void Play() { cout<< "Wav Play" << endl; }
			}


			class CMp3 : public CSound
			{	
				public:
					virtual void Play() { cout<< "Mp3 Play" << endl; }
			}


			class CFlac : public CSound
			{
				public:
					virtual void Play() { cout<< "FLAC Play" << endl; }
			}


			...

			class CSoundPlayer
			{
				CSound* _pSound;

				public :
					void SetFile( CSound* pSound )	{ _pSound = pSound }
					void Play() { _pSound.Play(); }
			}


			void main()
			{
				CSoundPlayer sPlayer;

				sPlayer.SetFile( new CMp3() );
				sPlayer.Play();

				sPlayer.SetFile( new CWav() );
				sPlayer.Play();

			}

3>	리스코프 치환 원칙..
	( Liskov Substitution Principle, LSP )
=========================================================================================

	-	부모 클래스와 자식 클래스 사이의
		행위에는 일관성이 있어야 함..

		-	부모 클래스의 인스턴스 대신
			자식 클래스의 인스턴스를 사용해도
			문제가 없어야 함..


		-	예)

				수정 전)

					class Bird
					{
						public:
							
							virtual void fly()
							{
								console.log("Flying");
							}
					}


					class Penguin : public Bird
					{
						public :
						
							// 리스코프 치환 원칙 위반 예시..
							virtual void fly()
							{
								throw new Error("Penguins can't fly!");
							}
					}


				수정 후)
									

					class NonFlyingBird

						...

4>	인터페이스 분리 원칙..
	( Interface Segregation Principle, ISP )
=========================================================================================

	-	인터페이스란..
		[ 참고 : https://ko.wikipedia.org/wiki/%EC%9D%B8%ED%84%B0%ED%8E%98%EC%9D%B4%EC%8A%A4_(%EC%BB%B4%ED%93%A8%ED%8C%85) ]

		-	서로 다른 두 개의 시스템이나
			장치 사이에서 정보나 신호를
			주고받는 경우의 접점이나 경계면..

		-	상호작용이나 커뮤니케이션에
			필요한 매개체..


	-	인터페이스를 잘게 분리함으로써,
		클라이언트의 목적과 용도에 적합한
		인터페이스 만을 제공..

	-	클래스는 자신이 사용하지 않는
		인터페이스는 구현하지 말아야
		한다는 원칙..

		-	하나의 일반적인 인터페이스 보다
			여러 개의 구체적인 인터페이스가 나음..


	-	SRP vs ISP
	
		공통점 : 단일 책임 원칙..
		차이점 : 단일 책임 원칙의 적용 대상..
				ㄴ	클래스 vs 인터페이스..

		// 문제 메세지 전송 기능..
		virtual void message(String number, String text) = 0;
	}
 
	class WirelessChargable {
		
		// 무선 충전 기능..
		virtual void wirelessCharge() = 0;
	}
 
	class ARable {

		// 증강 현실(AR) 기능..
		virtual void AR() = 0;
	}
 
	class Biometricsable {

		// 생체 인식 기능..
		virtual void biometrics() = 0;
	}


	class S21 : public IPhone, public WirelessChargable, public ARable, public Biometricsable
	{
		public :
			void call(String number) { }
 
			void message(String number, String text) { }
 
			void wirelessCharge() { }
 
			void AR() { }
 
			void biometrics() { }
	}


	class S3 : public IPhone
	{
		public:

			void call(String number) { }

			void message(String number, String text) { }

5>	의존성 역전 원칙..
	( Dependency Inversion Principle, DIP )
=========================================================================================

	-	의존 관계를 맺을 때, 변화하기 쉬운것 보단
		( Has A )		
		변화하기 어려운 것에 의존해야 함..

		-	
			===========================================
			변하기 쉬운 것..		|	구체적인 것..
								|	실제 기능..
			===========================================
			변하기 어려운 것..	|	추상적인 것..
								|	공통의 인터페이스..
								|	추상 클래스..
			===========================================

	-	자식 클래스에 수정이 필요한 경우,
		부모 클래스까지 변경해서는 안됨..

	-	구체적인 클래스보다
		인터페이스나 추상 클래스를 이용하여
		의존 관계를 구성할 것..


	---------------
	-	DIP 위반 !!
	---------------


		class Light {
			public void turnOn() {
				System.out.println("Light is turned on");
			}
		}

		class Switch {
			private Light light;

			public Switch() {
				this.light = new Light();
			}

			public void press() {
    			light.turnOn();
			}
		}

		public class Main {
			public static void main(String[] args) {
				Switch lightSwitch = new Switch();
				lightSwitch.press();
			}
		}

		ㄴ	[ Switch 클래스 ]는 [ Light 클래스 ]에
			직접적으로 의존..

			ㄴ	[ Light 클래스 ]가 변경되거나
				새로운 기능을 추가하려면
				[ Switch 클래스 ]도 수정해야 함..

				ㄴ	코드의 결합도를 높이고,
					유지 보수를 어렵게 만듬..


	---------------
	-	DIP 준수 !!
	---------------

		// 추상화..
		interface Device {
			void turnOn();
		}

		// 저수준 모듈..
		class Light implements Device {
			@Override
			public void turnOn() {
				System.out.println("Light is turned on");
			}
		}

		class Fan implements Device {
			@Override
			public void turnOn() {
				System.out.println("Fan is turned on");
			}
		}

		// 고수준 모듈..
		class Switch {
			private Device device;

			// 의존성 주입..
			public Switch(Device device) {
				this.device = device;
			}

			public void press() {
				device.turnOn();
			}
		}

		public class Main {

			public static void main(String[] args)
			{
				Device light = new Light();
				Device fan = new Fan();

				Switch lightSwitch = new Switch(light);
				lightSwitch.press();

				Switch fanSwitch = new Switch(fan);
				fanSwitch.press();
			}
		}

		ㄴ	[ Switch 클래스 ]는
			[ Device 인터페이스 ]에 의존..

			ㄴ	[ Light ]나 [ Fan ]의
				세부 구현에는 의존하지 않음..

		ㄴ	새로운 디바이스를 추가하려면
			[ Device 인터페이스 ]를
			구현하기만 하면됨..

			----------------
			-	의존성 주입..
				(Dependency Injection)
			----------------

				-	외부에서 두 객체 간의 관계를
					결정해주는 디자인 패턴..
					
				-	인터페이스를 사이에 둬서 클래스 레벨에서는
					의존관계가 고정되지 않도록 하고
					런타임 시에 관계를 동적으로 주입하는 방식..

				-	유연성을 확보하고 결합도를
					낮출 수 있게 해줌..
